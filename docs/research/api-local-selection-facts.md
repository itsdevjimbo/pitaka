# API local selection: publication and record facts

Research for [Establish the deploy API record and publication facts for selection](https://github.com/itsdevjimbo/pitaka/issues/202), checked 2026-09-28. This records facts for later decision tickets; it does not choose the selection policy.

## Deploy record contract

- The private deploy repository's [`versions/local.json`](https://github.com/itsdevjimbo/pitaka-deploy/blob/main/versions/local.json) is `schemaVersion: 1`, `environment: local`. Its current `api` value has exactly these fields: `repository`, `sourceSha`, `sourceTag`, `image`, `digest`, `platform`. It currently pins source `b88f0aabed08545f44cb845a8e12490b1992b936` and digest `sha256:2b9698dddb116e1686b79bd1d44ba3f577aa1c96eca5a94ef19a67a6c5f942e5`; `platform` is `linux/arm64`. The `web`, `images`, and `configuration` sections hold independent state.
- The [`validateVersion` implementation](https://github.com/itsdevjimbo/pitaka-deploy/blob/main/pitaka_deploy/versions.mjs) requires `api.repository` to equal `jimbodev0530/pitaka-api`; `sourceSha` to be 40 lowercase hex characters; `sourceTag` to equal `sha-` plus that SHA; `digest` to match `sha256:` plus 64 lowercase hex characters; `image` to equal `${api.repository}@${api.digest}`; and `platform` to be `linux/amd64` or `linux/arm64`. It also validates the rest of the complete record, including the web selection and supporting image pins. These are structural checks; the validator alone does not prove that a registry digest belongs to the source SHA.
- The [deploy README](https://github.com/itsdevjimbo/pitaka-deploy/blob/main/README.md) says the API reference is an image **index** digest and the fixed tag is provenance. Its preflight checks architecture and source revision. The deploy repo's `npm run apply` is a separate explicit operation; changing the record does not itself replace containers.

## Current API publication path

- [`.github/workflows/build.yml`](https://github.com/itsdevjimbo/pitaka/blob/main/.github/workflows/build.yml) starts on completion of `Code Quality and Tests`. `publish` runs only when that run succeeded, was a push to `main`, and came from this repository. It checks out the source run's `head_sha`, then runs [`publish-images.sh`](https://github.com/itsdevjimbo/pitaka/blob/main/scripts/publish-images.sh). A second job, `advance-main-tags`, needs `publish` and is serialized across API `main` tag changes.
- [`publish-images.sh`](https://github.com/itsdevjimbo/pitaka/blob/main/scripts/publish-images.sh) builds and pushes `jimbodev0530/pitaka-api:sha-<full SHA>` for `linux/amd64,linux/arm64`, with source revision both as an index annotation and platform config label. If the fixed tag already exists, the script reuses it only after validation. It then runs the [smoke script](https://github.com/itsdevjimbo/pitaka/blob/main/scripts/smoke-published-images.sh), which pulls that fixed tag, checks the config revision label, runs its migration bundle against disposable services, and waits for the API endpoint. The same image supplies runtime and migration bundle.
- [`container-images.sh`](https://github.com/itsdevjimbo/pitaka/blob/main/scripts/lib/container-images.sh) validates an index's `org.opencontainers.image.revision` annotation and that its Linux manifest architectures are exactly `amd64,arm64`. It does **not** return or persist an index digest.
- [`update-main-image-tags.sh`](https://github.com/itsdevjimbo/pitaka/blob/main/scripts/update-main-image-tags.sh) resolves the live `origin/main` SHA, validates that SHA's fixed image, creates the moving `main` alias from it with a source-revision index annotation, and validates the alias. An older publisher run can therefore promote a newer source SHA if its fixed image is ready. If the branch moves during promotion, the script retries against the newer SHA up to three times; it fails after continued movement. It can exit successfully while leaving the tag unchanged if the newer current tip's image is not ready. Thus a successful `advance-main-tags` job is not, by itself, proof that its triggering workflow run's `head_sha` is the current alias's source SHA or that the alias moved.

## Digest and trustworthy identity

- Docker's [image digest documentation](https://docs.docker.com/dhi/explore/security-concepts/digests/) distinguishes the multi-platform index digest from the platform manifest digests. The deploy record needs the former. [`docker buildx imagetools inspect`](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/) reports the index `Digest:` and can return structured `.Manifest` data or the raw index. The handoff can inspect a tag and then inspect `repository@sha256:<reported-index-digest>` to check its revision annotation and platform descriptors. It should take the digest from the registry/index response, not from a child manifest or local `docker image inspect` result.
- [`imagetools create`](https://docs.docker.com/reference/cli/docker/buildx/imagetools/create/) says a single index source normally gets a carbon copy, but the command also supports an `index:` annotation and can emit its result digest with `--metadata-file`. The current promoter supplies an index annotation when creating `main`. It should **not assume** that `main` and the fixed SHA tag have the same index digest without inspecting both. In the [Docker Hub repository view](https://hub.docker.com/repository/docker/jimbodev0530/pitaka-api/general) checked 2026-09-28, current `main` and `sha-b88f0aabed08545f44cb845a8e12490b1992b936` both showed index digest `sha256:397e0abd172ab04637c5fd1882aaf5e9f1228085836876dfdd69ab538e461e1f`. This is one observed pair, not a contract for future pushes. The older digest pinned in the deploy record differs from the current digest shown for that same fixed tag, so the fixed tag's immutability is a repository publication **policy**, not registry-enforced immutability or a verified historical fact.
- A downstream `workflow_run` receives identifiers for a completed upstream run. [GitHub's event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run) warns that the triggered workflow can access secrets/write tokens and that untrusted code or artifacts can compromise it. [Get a workflow run](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run) exposes the run's repository, event, branch, `head_sha`, status, conclusion, workflow ID, and attempt; [List jobs for a workflow run](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run) exposes each job's name and conclusion. A candidate verification path is to use the event only for the run ID, fetch that exact run and its jobs through GitHub's API, require the expected repository/workflow/push-to-main/success and a successful `advance-main-tags` job, then independently inspect the registry index and current Git `main` ref. GitHub's [Get a reference](https://docs.github.com/en/rest/git/refs#get-a-reference) supplies the live branch SHA. This describes available evidence; the selection gate remains to be decided.

## Open uncertainty for the next decision

- Direct registry inspection from this sandbox was blocked by network restrictions. Docker Hub's signed-in UI supplied the current tag digests, but this research did not read the raw current index bytes. The later design should specify the exact registry read and comparison, and handle a tag changing between reads. It also must decide whether to pin the verified fixed-tag index or the moving alias index, and how to interpret a successful promoter that deliberately left `main` unchanged.
