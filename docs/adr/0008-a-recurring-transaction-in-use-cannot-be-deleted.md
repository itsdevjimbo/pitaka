# A recurring transaction in use cannot be deleted

`DELETE /api/recurring-transactions/{id}` succeeds unconditionally on a person's own schedule (`RecurringTransactionsController.cs:184`). One relationship absorbs the consequences — `Transaction.RecurringTransaction` is configured `OnDelete(DeleteBehavior.SetNull)` (`PitakaDbContext.cs:101`) — so a single `204` nulls `RecurringTransactionId` on every Transaction the schedule ever generated. Nothing else in the model points at a `RecurringTransaction`, so that one foreign key is the whole blast radius.

**A recurring transaction is in use once a Transaction points at it, and one in use cannot be deleted.** One `409`, one sentence, and the schedule is cancelled instead.

As in ADR 0004, nobody chose `SetNull`; it reads as EF's default for an optional foreign key. Unlike ADR 0004, the default has a test asserting it — `Delete_ReturnsNoContent` (`:939`) seeds a generated transaction and checks that its `RecurringTransactionId` comes back null. Whether that test recorded a decision or merely wrote down what EF did, it now reads as the former, which is why it is rewritten rather than simply dropped.

## What is lost is the reading, not the record

ADR 0004's strong case was a **recorded fact** quietly going missing: three years of gym spending becoming uncategorised without a Transaction being edited. This is not that case, and it is worth being precise about the difference rather than borrowing the argument.

The money here is untouched. The Transactions stay, their amounts stay, `Account.CurrentBalance` stays correct. Nothing the person wrote down is lost — they never wrote down `RecurringTransactionId`; the API did. What is lost is the API's ability to read its own rows correctly, and two shipped features branch on exactly the bit that disappears:

- **`TransactionResource.TransactionDateForWire` (`:36`)** picks a time frame from `t.RecurringTransactionId is null`. A generated transaction dated `2026-09-01` is a wall-clock day with no instant behind it. Orphaned, it is stamped `DateTimeKind.Utc` and goes out as `2026-09-01T00:00:00Z` — a naive midnight silently promoted to a moment. That is #71's fix running backwards on a row nobody touched.
- **`TransactionService.GetPageForUser` (`:71-81`)** branches on the same expression to decide which of ADR 0005's two comparisons a row gets. The row changes frames mid-history, so a `from`/`to` window that used to contain it may stop containing it, or start.

So the failure is quiet in ADR 0004's sense — no screen looks wrong, nothing announces it — but the mechanism is different, and the difference matters for where the fix belongs. ADR 0004 protected a value because a person had authored it. This protects a value because the code reads it. `CONTEXT.md` states the same thing in the glossary: a recorded and a generated transaction "are told apart by `RecurringTransactionId` being null". After the delete that sentence is false of a row that genuinely was generated, and there is no other way to ask the question.

## `init` does not survive a foreign key

ADR 0007 made `Transaction.RecurringTransactionId` `init`, and named this field specifically: flipping it "retroactively changes what a past timestamp *means* on the wire, which is a live claim if anything is."

That protection is real against C#, and empty against the database. `SetNull` is a write the model never performs and never sees — EF issues it as part of the delete, or the database does it under the constraint. The compiler says this field may never change; MySQL changes it on an unrelated delete. A reader who finds `init` on the property is entitled to conclude the value is stable, and would be wrong.

This is the same gap ADR 0003 and ADR 0004 both closed by refusing to stop at a guard: ADR 0003 made `Category.Type` `init` so re-adding an assignment is a compile error, ADR 0004 moved four foreign keys to `Restrict` so the cascade could not resurrect the defect behind the controller's back. Here the two halves have simply been done in the wrong order — the `init` shipped in #96, the schema never followed. This ADR is the missing half, not a new precaution.

## Why refusal rather than a durable flag

There is a real alternative, and it is sitting in the model already. `Transaction.IsRecurring` survives the cascade untouched — it is a plain column, and nothing nulls it. Keep it (renamed `IsGenerated`, honestly), teach `TransactionDateForWire` and the filter to read it instead of the foreign key, and the schedule stays freely deletable while both readers keep working.

That works, and it is rejected on what it says rather than on cost.

It declares the link disposable and the provenance a boolean. "Was this generated?" stays answerable; "by what?" stops being, permanently and with no way back. A description reading `"Generated by recurring transaction: Rent"` (`GenerateTransaction.cs:17`) is prose, not a fact any code can read, and it is not a reason to call the provenance recoverable.

It also re-creates the duplicate the project is in the middle of removing. Two fields would state one fact, they would be allowed to disagree, and the discipline that keeps them agreeing would be that everyone remembers to set both — which is what `GenerateTransaction.cs:18` does by hand today, and what `TransactionFactory.cs:29` derives by hand in the tests. #94 exists because that arrangement does not hold. Rebuilding it deliberately, one issue later, would need an argument stronger than "it lets a delete keep working."

## The escape hatch already shipped

ADR 0004 could not ship a refusal alone without owing something: telling a person that a category they used once three years ago is theirs forever is the pressure that makes people delete things. It committed to `Retired` and filed it as #86, and the split needed the whole of ADR 0001 to justify.

None of that applies here, because the other half is already built. `RecurringTransactionStatus.Cancelled` is in the enum, `PATCH /api/recurring-transactions/{id}/status` (`:163`) sets it, and `PatchStatusAsync` (`:79`) writes any non-`Active` status without argument. The way out of a schedule the person is done with exists and has shipped; only the door that destroys history needs closing. There is no pair to split, no follow-up issue, and no ADR 0001 exception to record — this is a defect fix in that ADR's own terms, a query, a branch and a migration, and it changes no wire field in either direction.

Two behaviours fall out of using `Cancelled` for this, and both are consistent with what the glossary already says:

- A cancelled schedule stays in `GET /api/recurring-transactions` — `GetAllForUser` (`:22`) does not filter on status. Same as a retired Account staying in the account list among the active ones.
- `PatchStatusAsync` allows `Cancelled` back to `Active`. Also the same: leaving everyday use is reversible, in `CONTEXT.md`'s words "can be brought back".

Whether cancelling should be one-way is a question about the status machine, and this ADR does not answer it.

## Enforcement in two layers

Layer one is `RecurringTransactionService.HasGeneratedTransactionsAsync(int recurringTransactionId)` and a `409` in the controller, after the existing `Forbid`. The check needs no user scoping — the `Forbid` has already established ownership and a Transaction cannot point at another person's schedule — which is the same reasoning, and the same comment-not-a-`WHERE` conclusion, that ADR 0004 reached for `IsInUseAsync`.

The name says what it checks rather than what the verdict is called. `IsInUseAsync` earned its abstraction across four referents; one clause does not, and *generated transaction* is the glossary's own term for what the clause counts.

Layer two is the schema: `Transaction.RecurringTransaction` moves from `SetNull` to `Restrict`. This is not novel — `Transaction.Category` (`:95`) and `GoalContribution → Transaction` (`:107`) are both already `Restrict`, both paired with a `409` for the same reason. It is also the layer that matters most here, because the value being protected is one the *model* reads rather than one a person maintains, and a bulk cleanup or a seeder change that never touches the controller would otherwise reopen the whole thing.

## Considered options

**Refuse the delete once the schedule has generated anything.** Chosen.

**Keep the delete; move the discriminator to a durable flag.** Rejected above. It is the only alternative that fully preserves both readers, which is why it gets a section rather than a line.

**Refuse only when the person would notice — say, only for schedules that generated a transaction in the last N months.** Rejected without much deliberation. It makes correctness a function of the calendar, and the row it would let go is precisely the old one whose date frame nobody is watching.

**Cascade-delete the generated Transactions with the schedule.** Rejected. It answers a data-integrity problem by destroying more data, and it breaks the balance either way. Done at the database, the rows vanish without `ReverseTransaction` running and `Account.CurrentBalance` keeps their effect forever, disagreeing with a history that no longer contains them. Done in the service, the reversals run and the balance is silently restated. The first is corruption and the second is arguably correct, but nothing about "I no longer want this standing instruction" says "and unspend the rent."

**Accept and document.** Rejected. It leaves two shipped features — #71's serialisation and ADR 0005's filter — reachable by a `204` on an unrelated endpoint, and leaves ADR 0007's `init` making a promise the schema breaks.

## Consequences

- **A schedule that has run even once can never be deleted, only cancelled.** The same cost ADR 0004 accepted for Categories, minus the part that made it hard: the escape hatch exists today, so nobody is stuck while a follow-up waits for a screen.

- **Whether `pitaka-web` can reach that escape hatch is unverified.** Its `SchedulesService` calls `/api/recurring-transactions` (`CONTEXT.md`); whether it calls the delete, and whether it exposes cancelling, has to be checked before this merges. If it deletes and cannot cancel, the client change is a precondition rather than a follow-up — this is the one way the refusal could strand someone.

- **Rows orphaned before this ships stay orphaned, and `Restrict` cannot help them.** A Transaction with `RecurringTransactionId IS NULL AND IsRecurring = 1` was generated by a schedule that is already gone. The foreign key cannot be restored — there is nothing to point at — and `IsRecurring` is the only remaining record that the row was generated at all. **#94 drops that column**, so the count has to be taken before #94 lands, not after. If it is zero, #94 proceeds. If it is not, what to do with those rows is a decision about data and belongs in its own discussion.

- **This unblocks #94 rather than competing with it.** Once the foreign key cannot be nulled, `IsRecurring` is genuinely a duplicate of a fact that no longer disappears, and removing it loses nothing. Before this, removing it would delete the last evidence of the orphaning — evidence nothing reads, but evidence.

- **A race between the check and the delete surfaces as a 500.** A generated transaction created between `HasGeneratedTransactionsAsync` returning false and `SaveChangesAsync` hits `Restrict` and throws `DbUpdateException`. Accepted for the reason ADR 0004 accepted it, and more comfortably: the only writer that could win that race is the generator, which is not concurrent with a person's delete.

- **`Restrict` collides with `User → RecurringTransaction` being `Cascade` the day profile deletion arrives**, exactly as ADR 0004 recorded for `User → Category`. Same non-problem for the same reason: there is no user-delete path, and a "delete everything I have" flow that leans on foreign-key cascade ordering is not one to trust.

- **`CONTEXT.md`'s In use entry widens.** It is written Category-first — "A Category is in use once anything points at it" — and now states one rule over two entities: a Category with anything filed under it, and a recurring transaction that has generated a Transaction. The API's wording still differs per entity, because each `409` says what the thing *has* rather than naming the state; that is a message, not a term. **Retired** stays Account-and-Category: a recurring transaction cancels, and that word is already in the enum.

- **The delete endpoint keeps its `204`.** A schedule created and abandoned before its first run deletes exactly as it does today. The rule is about history, not about status — a *paused* or *cancelled* schedule with generated transactions is refused too, which is the same coming-apart of "in use" and "in effect" that ADR 0004 noted for a paused recurring transaction pinning its category.
